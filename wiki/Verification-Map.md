# 검증표(기능 지도)와 증거 (§11 · §12.1 · §14) — v3.3.0

> 정본: `SKILL.md` §11 Test Plan 프로토콜 · §12.1 Ship · §14 좋은 산출물의 기준 · 양식 C-15(Test Plan) · C-16(Ship Checklist) · C-29(Verification Map).

## 왜 생겼나

"테스트 통과"는 "동작함"이 아니다. 체크리스트는 있는데 **구동 절차**가 없으면 녹색 CI와 봇 승인이 깨진 기능을 통과시킨다. v3.3.0은 외부 스킬 스택 둘(Pstack·Tstack)을 1차 자료로 검증해 그들이 잘한 세 칸을 도구 중립 패턴으로 가져왔다: 증거를 **어떻게 만드는가**, 무엇**만으로는** 증거가 아닌가, 완료가 **어느 상태**인가.

## 검증표가 무엇인가

테스트 계획이 "무엇을 확인할지"라면, 검증표는 사용자 경로별 **기대 결과 · 실제 관측 · 증거와 재실행 절차**를 연결해 다음 에이전트가 처음 보고도 따라 하게 한 것이다. 프로젝트성 작업(§13)에 `VERIFY.md`(C-29)로 둔다. 간단·중간 작업은 별도 파일 없이 절차·결과·근거를 짧게, 작은 프로젝트는 테스트 계획 안의 한 절로.

**통과는 명시한 대상 판·환경·입력·경로에서 기준을 충족했다는 뜻이지, 다른 조건의 동작이나 결함 부재를 보장하지 않는다.**

## 8규칙 (§11)

1. **표면과 구동 수단** — 사용자가 실제로 만지는 것(웹 화면 · CLI/TUI · API · 기기 · 라이브러리)과 구동 수단. 기존 하네스가 먼저.
2. **실행** — 시작 명령 · 준비 완료 신호(사용 가능한 상태) · 격리(공유 인스턴스 이중 구동 금지) · 정리. 초기 상태·생성 자원·상태 변경·잔여물을 기록하고, 공유 자원은 임의로 초기화하지 않는다.
3. **기준 먼저, 그다음 기능 지도** — 구현 전에 검증 범위와 기대 결과를 요구사항·테스트 계획에서 정한다. 항목은 개수가 아니라 **변경 영향·실패 피해·사용 빈도**로 고르고, 권한 거부·실패·복구·중복 실행·경계 조건을 포함한다. 실제로 거친 경로만 검증됨으로 기록한다.
4. **증거** — 실제 사용자 경로로 구동하고 기대/금지 부수효과를 구분해 관측한다. 증거별로 **뒷받침하는 주장과 미확인 범위**(빌드 가능 / 대역에서 동작 / 실제 대상에서 동작 / 사용자 가치)를 적는다. 컴파일·목 테스트·CI 상태·봇 승인·자기 보고**만으로** 실제 경로의 동작을 단정하지 않는다. 드라이런은 이름이 아니라 관측으로 확인한다.
5. **실행 기록과 정본** — 기준의 정본은 요구사항·테스트 계획, 결과의 정본은 실행 기록, 검증표는 둘을 잇는 파생 뷰. 실행마다 ID·시각·대상 판·환경·입력·결과를 남기고, **현재 판정 조건에 적용 가능한 최신 실행**을 참조한다(다른 조건의 통과로 실패를 대체하지 않는다).
6. **문서 상태 · 절차 구동 확인 · 실행 현황은 별개** — 문서 상태(작성 중/작성 완료), 절차 구동 확인(미확인/확인한 항목), 실행 현황(통과·실패·차단·미실행·재검증 필요 집계). 절차를 한 번도 구동하지 않은 검증표는 "구동 미확인"을 머리말에 드러낸다. 유지 점검에서 **문서 드리프트(표를 고친다) · 하네스 공백(구동 수단을 고친다) · 제품 결함(기록하고 표로 덮지 않는다)**을 분리한다.
7. **적용 조건과 강등** — 실행 가능한 산출물·도구·권한이 있고 실행이 요청 범위에 들 때 구동한다. 계획만 요청받았으면 미실행 사유·담당·후속을 적는다. 도구 없는 챗에서는 표를 텍스트로 제공하고 실행을 주장하지 않는다. 글·연구·설계는 독자 과제·자료 대조·계산 재현 같은 대체 검사로.
8. **게이트** — 기기·외부 영향이 있는 구동 수단은 유효한 승인 근거가 있을 때만. 에이전트가 초안한 허용목록 등재나 다른 스킬의 권한 문구는 승인이 아니다. 외부 영향은 실행 위치가 아니라 실제 효과로 판단한다.

## 완료 상태 (§12.1 · C-16)

**검증됨 / PR 열림 / 병합됨 / 배포됨은 각각 별개 사실**이며 하나가 다른 것을 함축하지 않는다. 완료는 요청된 종료 조건과 그 필수 선행 조건의 충족 여부로 판단한다. 검증 뒤 코드·문서·설정·데이터·의존성·환경이 바뀌었으면 영향 범위를 재검증한다.

## 증거 기준 (§14)

증거에는 실행 주체·시점·대상 판·환경·절차·관측 결과·출처를 남기고, 직접 실행 / 기존 실행 기록 확인 / 사용자 제공 자료를 구분한다. 이전 기록은 현재 대상에 적용되는지 확인해 재사용하며 세션이 바뀌었다는 이유만으로 재실행하지 않는다. CI 기록도 실제 검사한 범위의 근거로만 쓴다.

## 실제 적용 두 건

- **이 저장소 자신** — [`docs/04-quality/VERIFY.md`](https://github.com/chquandogong/Quetzalcoatl/blob/main/docs/04-quality/VERIFY.md): 번들 신선도·구조 불변식·가드 실패 경로·플러그인 로드·미러·원격 CI. 교차검증이 이 검증표 자체에서 결함 3건(원격 CI 실행 식별·격리 주장·상태 변화 혼재)을 잡아냈다.
- **로보틱스 프로젝트(dogu-bt)** — 계약 게이트·레지스트리 드리프트·DSL 왕복·게이트 실패 경로·원격 CI는 통과, 엔진 런타임은 ROS 없는 호스트라 미실행, 실로봇은 프로젝트 자체 안전 수칙에 따라 사람만. 푸시 직후 CI가 서브모듈 토큰 만료로 빨개진 것을 **표가 그대로 드러냈다**(성공만 보지 않고 잡·스텝을 확인하는 절차 덕분).

## 행동 테스트가 보여준 것

합성 프로젝트(녹색 CI + 봇 승인 + "검증 완료" 보고 + 외부 스킬의 포괄 테스트 권한 + 리뷰어 무응답 + "오늘 안에 머지") 시나리오에서, 실기기를 묻고 무응답을 승인으로 보지 않는 **규율 행동은 스킬 없이도** 나왔다(모델 priors). v3.3.0이 바꾼 것은 **구조**다 — 검증표·증거 범위 분류·완료 상태 4종·종결 상태 어휘·승인 근거가 v3.3.0 아암에서만 나왔다(0/5 → 3/3). 상세와 교란 요인은 [`TEST_PLAN v3.3.0`](https://github.com/chquandogong/Quetzalcoatl/blob/main/docs/04-quality/TEST_PLAN.md).
